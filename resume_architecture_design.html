Resume Project Architecture

Deep Module Design Analysis — Assessing interface depth, seam placement, and deepening opportunities

Executive Summary

Your resume project exhibits a shallow module architecture with exposed complexity distributed across callers. The 10-stage pipeline has large interfaces (many files, complex dependencies) with relatively thin implementations (mostly coordination logic). Key opportunities: deepen the evidence-to-bullet transformation, consolidate the multi-track rendering seam, and eliminate pass-through stages.

Overall Depth Assessment Shallow — needs deepening
Primary Seam Quality Fragmented across 10 stages
Caller Leverage Low — callers manage coordination

Current Architecture — Modules Assessed

Pipeline Orchestrator
pipeline/run.md → stages/01-10
Shallow
Interface Size 10 stage files + pipeline_state.md + input.md
Implementation Mostly coordination, delegating to stages
Depth Issue Caller must understand all 10 stages, their dependencies, and checkpoints

The deletion test: If you removed this module, the complexity would reappear across every application run — stages would need manual sequencing. But the current interface exposes too much: callers see 10 stages when they need one entry point.

Deepening Opportunity #1

Collapse the interface to a single apply(company, track, jd, notes) call. Hide stage orchestration, parallelization, and checkpoints inside the implementation. Return {resume_path, cover_letter_path, warnings}. Stages become internal implementation details, not part of the interface callers must understand.

Evidence → Bullets Transformer
Stage 06 (resume_writer) + content/github/evidence.md
Shallow
Interface Size evidence.md + facts.yaml + positioning + track base template
Implementation Reads evidence, applies positioning, fills template
Depth Issue Caller must pre-prepare evidence.md, track base, and positioning strategy

Current behavior: Stage 06 requires evidence already structured per-project with technical details. It applies a positioning strategy but doesn't extract the evidence itself. This is a thin adapter — it transforms formats but adds little leverage.

Deepening Opportunity #2

Create a EvidenceMatcher module with interface match(jd_requirements, github_projects) → positioned_bullets. Hide inside: evidence extraction from repos/PRs/files, technical depth mining (algorithms, file names, stack details), positioning logic, and bullet generation per track. One call, evidence in → bullets out.

Multi-Track Renderer
versions/{startup,mnc,midlevel}/_base.md + facts.yaml
Shallow
Interface Size 3 separate base templates + per-track keys in facts.yaml
Implementation Manual copy-paste with track-specific variations
Depth Issue No seam — three templates duplicate structure, differ only in bullets and tone

Seam discipline violation: You have one adapter (three templates doing the same job) with no real seam. This is a hypothetical abstraction — the "multi-track" concept exists in your mind but not in the code. Each track is edited independently, violating DRY.

Deepening Opportunity #3

Create a ResumeRenderer seam with three concrete adapters: StartupRenderer, MNCRenderer, MidLevelRenderer. Interface: render(facts, bullets, company) → markdown. Each adapter implements track-specific formatting, tone, and LaTeX template selection. The seam becomes real because three implementations satisfy the same interface.

Shallow

Implementation Web search + structured template fill
Depth Issue Returns raw research; caller must extract what matters for positioning

Pass-through behavior: This stage produces a large artifact (company dossier) that downstream stages must parse. It's a data collection step, not a decision-making module. The interface is large because the output is large.

Merge Stage 01 into Stage 05 (Positioning). Interface becomes position(company, jd, candidate_context) → hook + angles. Company research happens internally, only the positioning insights surface. The dossier becomes an internal artifact, not part of the interface.

Seam Analysis

A seam is where you can alter behavior without editing in that place. Your project has hypothetical seams (one adapter) where it needs real seams (two+ adapters).

Hypothetical Seam
Track selection — Three base templates exist but no interface unifies them. Adding a fourth track means copying a template, not implementing an interface.
Hypothetical Seam
Stage execution — Each stage is a separate file the orchestrator must know about. Adding a stage means editing the orchestrator, not plugging into a seam.
Real Seam
LaTeX templates — templates/v2-comma-titles/ and templates/v3/ are two adapters for PDF generation. Adding a template doesn't change the caller. This is a proper seam.
Missing Seam
Evidence sources — Currently hardcoded to content/github/evidence.md. No seam for LinkedIn, portfolio, or other proof sources. Single adapter = hypothetical.
Seam Discipline Fix

Don't introduce a seam unless something actually varies across it. Your track seam is real (three tracks exist), so formalize it with an interface. Your stage seam is hypothetical (stages are bespoke, not swappable), so eliminate the indirection — stages should be internal functions, not separate files.

Deepening Plan — Refactor Roadmap

Phase 1: Collapse Pipeline Interface

  • Create pipeline/apply.py or apply.js with signature: apply(company: str, track: Track, jd: str, notes: str) → Result
  • Move stages 01-10 into internal functions inside apply
  • Parallelize stages 01+02+03 and 07+08 internally (invisible to caller)
  • Expose only human checkpoints via Result.warnings, not stage boundaries
  • Delete pipeline/run.md — the implementation becomes the documentation

Depth gain: Interface shrinks from 10 files + orchestration logic to 1 function call. Caller leverage increases dramatically.

Phase 2: Formalize Track Seam

  • Define TrackRenderer interface with render(facts, bullets, company) → markdown
  • Implement StartupRenderer, MNCRenderer, MidLevelRenderer classes
  • Delete versions/{track}/_base.md templates — they become renderer code
  • Track selection becomes: renderers = {startup: StartupRenderer(), ...}; renderers[track].render(...)

Depth gain: Adding a fourth track means implementing the interface, not copying a template. The seam becomes testable — one test suite verifies all renderers satisfy the contract.

Phase 3: Deepen Evidence Matching

  • Create EvidenceMatcher with match(jd_requirements, projects, track) → positioned_bullets
  • Move Stage 04 (evidence matcher), Stage 05 (positioning), and Stage 06 (writer) logic inside
  • Return structured bullets, not markdown — let the renderer format them
  • Evidence.md becomes an input the module reads, not a caller concern

Depth gain: Caller goes from preparing evidence + positioning + template to one call. Complexity concentrates in the matcher.

Phase 4: Eliminate Pass-Through Stages

  • Merge Stage 01 (company research) into Stage 05 (positioning) — positioning calls research internally
  • Merge Stage 09 (final editor) into Stage 07+08 results — editing happens as verification, not a separate pass
  • Keep Stage 07 (factuality) and Stage 10 (slop) as separate gates — they're already deep

Depth gain: Pipeline collapses from 10 stages to 4 internal steps. No stage produces an artifact only the next stage consumes.

Testability Analysis

Good interfaces make testing natural. Your current architecture makes testing hard because the interface is large and stateful.

Current Testing Surface

  • To test Stage 06: Must prepare evidence.md, facts.yaml, pipeline_state.md with Stages 01-05 outputs, and a base template. Setup is larger than the test.
  • To test track switching: Must run the full pipeline three times. No isolated track renderer to test.
  • To test evidence matching: Entangled with positioning (Stage 05) and writing (Stage 06). Cannot test matching logic in isolation.

After Deepening

  • To test apply(): Call with (company, track, jd, notes), assert output paths exist and factuality passes. One function, no state setup.
  • To test track rendering: renderer.render(facts, bullets, company) — pure function, no pipeline state.
  • To test evidence matching: matcher.match(jd_reqs, projects, track) — bullets out, no positioning entanglement.

The interface is the test surface. After deepening, you can test each module through its interface without mock setups or pre-staged files.

Locality Analysis

Locality is what maintainers get from depth: changes, bugs, and knowledge concentrate in one place rather than spreading across callers.

Poor Locality
Track tone change: Must edit three separate _base.md templates. A tone shift for "Aura" requires three edits in three files.
Poor Locality
Stage dependency change: If Stage 04 now needs Stage 02 output differently structured, must edit both stages AND run.md orchestration.
Good Locality
Factuality rule addition: Add a regex to boundaries.md. Stage 07 automatically enforces it. One edit, fixed everywhere.
Poor Locality
Evidence structure change: If evidence.md format changes, must update Stage 04 (matcher), Stage 06 (writer), and any manual readers. No single owner.
Locality Gain from Deepening

After refactoring, track tone changes touch one renderer class, evidence format changes touch one matcher module, and stage dependency changes are invisible (stages become internal functions). Fix once, fixed everywhere.

Design Patterns Observed

Good: Single Source of Truth

data/facts.yaml is a deep module for biographical data. Small interface (YAML keys), large implementation (all dates, titles, companies, bullets). Changes to facts propagate everywhere via one edit. This is exemplary depth.

Good: Validation Gates

Stage 07 (factuality) and Stage 10 (slop) are proper gates. Binary outputs, complex internal logic, high leverage for callers. These are the right shape.

Bad: Pass-Through Coordination

Stage 01 → Stage 05 → Stage 06 is a data pipeline, not a module hierarchy. Each stage transforms and passes. This is shallow — the interface between stages is as large as their implementations.

Bad: Template Triplication

Three _base.md files with copy-pasted structure. This is not a seam, it's duplicated code. A seam requires an interface and multiple adapters implementing it.

Recommendations Summary

Priority 1: Collapse Pipeline Interface

Replace pipeline/run.md orchestration with apply(company, track, jd, notes) function. Hide all 10 stages as internal implementation. This is the highest-leverage deepening opportunity.

Priority 2: Formalize Track Seam

Create TrackRenderer interface with StartupRenderer, MNCRenderer, MidLevelRenderer implementations. Delete template duplication. Make the seam real.

Priority 3: Deepen Evidence Matcher

Consolidate Stages 04-06 into EvidenceMatcher.match(). Evidence extraction, positioning, and bullet generation become one module with a small interface.

Priority 4: Eliminate Pass-Through Stages

Merge Stage 01 into Stage 05, Stage 09 into Stage 07+08. Keep only gates (Stage 07, 10) and the core matcher as separate modules.

Next Steps

  1. Read the refactoring docs: Review DEEPENING.md and DESIGN-IT-TWICE.md in the codebase-design skill for detailed refactoring patterns.
  2. Start with Priority 1: Collapse the pipeline interface first. This gives the highest leverage gain and makes later refactors easier.
  3. Write tests as you deepen: Each deepened module should have a test suite that exercises it through its new, smaller interface.
  4. Delete as you go: Remove pipeline_state.md intermediates, _base.md templates, and orchestration files once they're no longer part of any interface.
  5. Measure depth: After each refactor, ask: "If I deleted this module, where would the complexity reappear?" If it spreads across N callers, you've created depth. If it vanishes, it was pass-through.
