# Resume Best Practices Research
*Compiled from credible sources: September 13, 2026*

## Executive Summary

Four core principles emerged across all credible sources:

1. **Impact over responsibilities**: Quantify achievements using the formula "Accomplished [X] as measured by [Y] by doing [Z]" — metrics demonstrate value, duties only describe time spent.

2. **Length is not sacred**: The one-page rule is outdated. Two pages is now standard for professionals with 5+ years experience. Quality and relevance matter more than arbitrary limits. Recent graduates and career changers should still aim for one page.

3. **Startup vs MNC divergence**: Startups prioritize builders who ship fast, demonstrate ownership, and thrive in ambiguity. MNCs prioritize ATS optimization, keyword alignment, quantified scale metrics, and demonstrated impact at scope.

4. **Credibility is fragile**: Inflated claims, buzzwords without substance, and vague descriptions trigger immediate skepticism. Authenticity with specific, verifiable achievements builds trust.

## Section 1: Startup Resume Guidance

### What Founders Look For

**Core hiring criteria from Y Combinator and early-stage perspectives:**

1. **Shipping velocity over process adherence**
   - Evidence of completing projects end-to-end, not just contributing to features
   - Side projects, hackathons, personal ventures demonstrate initiative
   - "Launched X in Y weeks" signals better than "contributed to X over Y months"

2. **Ownership mentality**
   - Phrases like "identified problem," "designed solution," "implemented and deployed" show autonomy
   - Avoid passive constructions: "was responsible for" → "built," "shipped," "designed"
   - Demonstrate decisions made, not just tasks completed

3. **Technical versatility (T-shaped skills)**
   - Generalists with depth in one area but breadth across the stack
   - Ability to context-switch between frontend, backend, infrastructure, product
   - Hardware + software + AI breadth is a **strength** for startups, not dilution

4. **Comfort with ambiguity**
   - Projects with evolving requirements or pivots
   - Self-directed work (personal projects, open source) signals independence
   - Avoid over-emphasis on structured processes or big-company frameworks

5. **Scrappiness and resourcefulness**
   - Built with limited resources or constraints
   - Rapid prototyping, iteration based on feedback
   - "Bootstrapped," "self-funded," "built with zero budget" are positives

**What matters less for startups:**
- Perfect tech stack alignment (good engineers learn fast)
- Big-name company pedigree (can indicate over-reliance on resources)
- Advanced degrees unless research-focused role
- Years of experience (2-5 years can be ideal — experienced enough to be productive, not yet set in big-company ways)

### Structure & Format for Startup Resumes

**Length**: 1 page for recent graduates, 2 pages acceptable for substantial project portfolio

**Section priority (top to bottom):**
1. **Contact + Links** (GitHub, portfolio, LinkedIn) — founders will check your code
2. **Technical Skills** — lead with what you can build with today
3. **Experience** — emphasize personal projects equally with work experience
4. **Projects** — if separate section, focus on deployed/shipped work
5. **Education** — unless from top-tier CS program, put at bottom

**Visual approach:**
- Clean, scannable, but personality acceptable
- White space matters — don't cram
- PDF format, sans-serif fonts
- Consistent formatting signals attention to detail

### Content Strategy for Startups

**Bullet formula:**
- Action verb + what you built + technology stack + impact/outcome
- Example: "Built real-time voice agent using LiveKit WebRTC with Silero VAD, enabling sub-200ms interrupt latency for 1k+ test users"

**Emphasis areas:**
- **Shipped products**: Link to live demos, GitHub repos, app store listings
- **Technical ownership**: "Architected," "designed," "built end-to-end"
- **Speed metrics**: "Launched in 3 weeks," "Rapid prototyped in 48-hour hackathon"
- **User feedback loops**: "Iterated based on user feedback," "Pivoted approach after testing"
- **Resourcefulness**: "Built without external funding," "Optimized for edge deployment under memory constraints"

**Personal projects section:**
- Treat with equal weight to work experience
- Focus on projects that demonstrate:
  - Completion (not abandoned repos)
  - Real-world utility (solves actual problem)
  - Technical depth (not just API wrappers)
  - Documentation quality (signals communication skills)

**De-emphasize for startups:**
- Corporate processes, frameworks, approval chains
- "Worked with stakeholders," "coordinated with teams" (unless leadership role)
- Large team sizes (unless you led the team)
- Compliance, governance, enterprise requirements

### Common Mistakes for Startup Applications

**Red flags that trigger skepticism:**

1. **Over-engineering personal projects**
   - "Built scalable microservices architecture for todo app" signals lack of pragmatism
   - Startups want appropriate solutions, not resume-driven development

2. **Big-company language without translation**
   - "Drove alignment across cross-functional stakeholders" → founders want "shipped feature used by X users"
   - Process over outcome signals misaligned priorities

3. **Narrow specialization**
   - "Expert in React hooks optimization" without showing full-stack ability
   - Startups need breadth; hyper-specialization suggests inflexibility

4. **Lack of side projects or curiosity**
   - For engineers, no personal projects signals you code only when paid
   - Missing GitHub profile or empty repos raise questions about passion

5. **Inflated claims about unvalidated work**
   - "Built production-ready platform" when it's a personal prototype with no users
   - "Scaled to millions of users" when you deployed to Vercel with zero traffic

### Cold Email & Application Strategy for Startups

**Best practices from research:**

1. **Direct founder outreach often beats application portals**
   - Find founder email (company domain, LinkedIn, Twitter/X)
   - Subject line: "Engineer interested in [specific problem company solves]"
   - Keep to 3-4 paragraphs maximum

2. **Email structure that works:**
   - **Line 1**: Who you are in one sentence (not generic introduction)
   - **Paragraph 1**: Why THIS company/problem interests you (specific, not generic)
   - **Paragraph 2**: 2-3 relevant technical achievements with links
   - **Paragraph 3**: What you could start building week one
   - **Close**: Ask for 15-min call, attach resume

3. **Timing matters**
   - Apply early after funding announcements (hiring ramp-up)
   - Follow up after 1 week if no response
   - Reference any mutual connections or investors

4. **Portfolio over resume for startups**
   - Live demo links in email > resume bullets
   - GitHub repos with good READMEs > listing technologies
   - Loom video of project walkthrough > written description

## Section 2: MNC/Big Tech Resume Guidance

### ATS & Recruiter Screening

**How technical resumes are evaluated at large companies:**

**Stage 1: ATS (Applicant Tracking System) — automated**
- Parses resume for keywords, job titles, skills, education
- Matches against job description requirements
- Scores candidates, surfaces top matches to recruiters
- ~60-80% of resumes never reach human review

**Stage 2: Recruiter screen — 6-7 seconds average**
- Quick pattern matching: company names, job titles, skills
- Looking for "obvious yes" signals: right keywords, relevant experience, top-tier companies/schools
- Decide: reject, maybe, or forward to hiring manager

**Stage 3: Hiring manager review — 30-60 seconds**
- Deeper evaluation of projects and impact
- Assessing technical depth and relevant experience
- Deciding whether to proceed to phone screen

**Optimizing for this pipeline:**

**ATS optimization (necessary but not sufficient):**
- Use standard section headers: "Work Experience," "Education," "Technical Skills," "Projects"
- Avoid tables, text boxes, headers/footers, graphics, columns
- Submit as .docx or PDF (check job posting preference)
- Include both acronyms and spelled-out terms: "NLP (Natural Language Processing)"
- Mirror language from job description (but don't keyword-stuff)
- Use standard fonts: Arial, Calibri, Helvetica, Times New Roman

**Keyword strategy:**
- Extract 15-20 keywords from job description
- Naturally incorporate 60-80% into resume
- Focus on: programming languages, frameworks, methodologies, tools, domain areas
- Example for AI Engineer role: Python, PyTorch, TensorFlow, transformers, fine-tuning, model optimization, REST APIs, AWS, Docker, CI/CD, Agile

**Format must-haves:**
- 10-12pt font size
- 0.5-1 inch margins
- Consistent bullet formatting
- Clear visual hierarchy
- No images, logos, or creative graphics

### Technical Bullet Writing

**The standard formula (appears in MIT, Stanford, McDowell, Orosz sources):**

**Action Verb + Task + Technology + Quantified Result**

**Example breakdown:**
- ❌ "Worked on improving model performance"
- ✅ "Optimized BERT model inference using TensorFlow Lite quantization, reducing latency by 45% (380ms → 210ms) while maintaining 94% accuracy"

**Strong technical action verbs by category:**

**Building & Creating:**
- Engineered, Architected, Developed, Built, Implemented, Designed, Created, Programmed

**Improving & Optimizing:**
- Optimized, Refactored, Enhanced, Streamlined, Automated, Reduced, Accelerated, Improved, Increased

**Leading & Collaborating:**
- Led, Spearheaded, Mentored, Coordinated, Collaborated, Drove, Established, Initiated

**Problem Solving:**
- Debugged, Resolved, Diagnosed, Fixed, Analyzed, Identified, Investigated, Troubleshot

**Avoid weak/vague verbs:**
- Responsible for, Worked on, Helped with, Involved in, Participated in, Contributed to (unless part of larger phrase)

### Quantifying Impact Without Inflating

**Legitimate metrics you CAN use:**

**Performance improvements:**
- Latency reduction: "Reduced API response time by 40% (500ms → 300ms)"
- Throughput: "Increased processing capacity from 1K to 5K requests/minute"
- Accuracy: "Improved model F1 score from 0.82 to 0.89 on validation set"
- Resource usage: "Decreased memory footprint by 60% through model quantization"

**Scale (when accurate):**
- Data processed: "Pipeline processing 2M records/day"
- Users (if you have real data): "Feature serving 10K daily active users"
- Code size: "Refactored 15K LOC codebase, reducing complexity by 35%"

**Time savings:**
- "Automated testing workflow, reducing CI/CD pipeline time from 45min to 12min"
- "Built internal tool saving engineering team 5 hours/week"

**For personal projects without users:**
- Technical metrics: model accuracy, inference speed, code coverage
- Development velocity: "Built in 3 weeks," "Shipped MVP in 2 sprints"
- Architectural scope: "Architected 5-service microservices system with event-driven messaging"
- DO NOT invent user counts, revenue, or production scale

**What NOT to quantify (evidence boundaries):**
- ❌ Users/traffic you don't actually have
- ❌ "Potential" or "projected" impact
- ❌ Revenue for non-commercial projects
- ❌ Taking credit for team achievements as individual metrics
- ❌ Downstream metrics you didn't directly influence

### Keywords & Skills Sections

**Structure for technical skills section:**

**Option 1: Categorized (preferred for experienced engineers)**
```
Technical Skills:
• Languages: Python, JavaScript/TypeScript, C++, Kotlin, SQL
• AI/ML: PyTorch, TensorFlow, Transformers, LangChain, RAG, Prompt Engineering
• Voice/Multimodal: LiveKit, WebRTC, Silero VAD, Deepgram, ElevenLabs
• Frameworks: React, FastAPI, Node.js, Jetpack Compose
• Tools & Platforms: Git, Docker, AWS, CI/CD, Vitest
```

**Option 2: Proficiency-based (for specialists)**
```
Technical Skills:
• Expert: Python, PyTorch, TensorFlow, NLP, Model Fine-tuning
• Proficient: FastAPI, Docker, AWS, React, TypeScript
• Familiar: Kubernetes, Go, Rust
```

**Option 3: Flat list (for ATS optimization)**
```
Technical Skills: Python • PyTorch • TensorFlow • JavaScript • TypeScript • React • FastAPI • Docker • AWS • Git • CI/CD • NLP • Computer Vision • REST APIs • WebRTC • Transformers
```

**Keywords by role (2026 trends):**

**AI/ML Engineer:**
- Must-have: Python, PyTorch OR TensorFlow, Transformers, Fine-tuning, Model Optimization
- Strong-plus: LLMs, RAG, Vector Databases, Prompt Engineering, LangChain, LlamaIndex
- Emerging: Agentic AI, Tool Calling, Multi-Agent Systems, Memory Management

**Software Engineer (AI-adjacent):**
- Must-have: Python OR JavaScript, REST APIs, Git, Databases (SQL/NoSQL), Testing
- Strong-plus: Docker, CI/CD, AWS/GCP/Azure, Microservices, System Design
- Emerging: AI Integration, LLM APIs, Real-time Systems, WebSockets

**Voice AI / Wearable AI Engineer:**
- Must-have: Real-time audio processing, WebRTC, STT/TTS, Streaming, Low-latency systems
- Strong-plus: Edge computing, On-device ML, Privacy-first design, Multi-modal AI
- Emerging: Agentic behavior, Context awareness, Memory systems, Wearable constraints

**Skills section best practices:**
- Only list skills you can discuss confidently in interview
- Order by relevance to target role
- Update for each application (reorder, emphasize)
- Include both tools AND domains (e.g., "Computer Vision" alongside "TensorFlow")
- Avoid rating systems (⭐⭐⭐) or vague terms like "familiar with"

## Section 3: AI/ML Role Specific Guidance

### Current Market Context (2026)

**Hiring trends:**
1. **Shift from research to applied AI**
   - Companies want engineers who can ship AI products, not just train models
   - Product thinking + technical depth valued over pure ML research
   - "Applied AI Engineer" role emerging as distinct from "ML Engineer"

2. **LLM integration skills in high demand**
   - Prompt engineering, RAG architectures, LLM tool calling
   - Evaluation frameworks, cost optimization, caching strategies
   - Multi-agent orchestration, agentic workflows

3. **Edge AI and on-device ML growing**
   - Wearables, mobile, IoT requiring on-device inference
   - Model quantization, pruning, distillation essential
   - Privacy-first architectures (on-device processing)

4. **Full-stack AI engineers premium**
   - Can build entire AI product: data pipeline → model → API → frontend
   - Understanding of both ML and software engineering best practices
   - DevOps for ML (MLOps) increasingly expected

### Positioning AI/ML Experience

**For candidates with internship + personal projects:**

**Lead with technical depth:**
- Specific models, architectures, techniques used
- Datasets, evaluation metrics, results
- Infrastructure and deployment considerations

**Example (good):**
"Fine-tuned Whisper-large-v3 on 50 hours of domain-specific audio achieving 12% WER improvement over base model; deployed with ONNX Runtime on ESP32-S3 with 4-bit quantization for real-time inference under 100ms latency"

**Example (weak/generic):**
"Used AI to build voice recognition system with high accuracy"

**Frame personal projects as R&D:**
- "Researched and implemented [technique] to solve [problem]"
- "Evaluated [approach A] vs [approach B] across [metrics]"
- "Prototyped [system] validating [hypothesis]"

**Demonstrate end-to-end thinking:**
- Don't just mention training models — show deployment, monitoring, iteration
- Include data collection/preparation, not just modeling
- Discuss tradeoffs (accuracy vs latency, model size vs performance)

### Domain-Specific Bullet Patterns

**Computer Vision:**
- "Trained YOLOv8 object detection model on custom dataset of 10K annotated images, achieving 0.85 mAP@0.5 and 30 FPS on mobile devices"
- "Implemented real-time semantic segmentation pipeline processing 1080p video at 15 FPS using DeepLabV3+ with MobileNetV2 backbone"

**NLP/LLMs:**
- "Built RAG system using FAISS vector search over 50K document embeddings, reducing hallucination rate by 65% in domain-specific QA"
- "Implemented multi-turn conversational agent with function calling for calendar/task automation, handling 95% of test scenarios without fallback"

**Voice AI:**
- "Architected real-time voice agent using LiveKit WebRTC with client-side Silero VAD, enabling sub-200ms interrupt latency and natural turn-taking"
- "Integrated streaming STT (Deepgram) with streaming TTS (ElevenLabs) in duplex mode, achieving <500ms end-to-end response time"

**MLOps/Infrastructure:**
- "Built automated model retraining pipeline with MLflow tracking, reducing manual intervention from 8 hours to 15 minutes per iteration"
- "Deployed multi-model serving infrastructure handling 10K predictions/sec with p99 latency <50ms using FastAPI + Redis caching"

### Addressing Experience Gaps

**For recent graduates/career changers:**

**Emphasize learning velocity:**
- "Self-taught [X] in Y months, shipping [concrete project]"
- "Completed [specific course/certification] and immediately applied to [project]"

**Reframe internships strategically:**
- Don't minimize internship work with qualifiers ("just an intern")
- Use same format as full-time roles
- Quantify impact where possible
- Show increasing responsibility if multiple internships

**Leverage open source contributions:**
- "Contributed to [well-known project]: [specific PR/feature]"
- Link to merged PRs, not just attempted contributions
- Frame as collaborative software engineering, not just solo coding

**Academic projects can count IF:**
- Non-trivial scope (not toy homework assignments)
- Real-world application or research contribution
- Well-documented and publicly available
- Frame as "Research Project" not "Class Assignment"

## Section 4: Personal Projects & Open Source

### How to Present Personal Projects Credibly

**Quality over quantity:**
- 2-3 substantial projects > 10 toy projects
- Each project should demonstrate different skills/domains
- Better to have fewer complete projects than many abandoned repos

**What makes a project "substantial":**
- Solves a real problem (even if niche)
- Non-trivial technical complexity
- Complete implementation (not prototype abandoned at 80%)
- Good documentation (README with setup, usage, architecture)
- Evidence of iteration (commit history shows evolution)

**Project description structure:**

**Template:**
"[Project name]: [One-line description] | [Tech stack]
• [Technical challenge addressed and approach]
• [Key architectural decisions or innovations]
• [Quantifiable outcome: performance metric, usage, learning, or technical achievement]"

**Example:**
"Mia — Personal AI Engineering OS | TypeScript, Bun, Multi-Host LLM Adapters, Vitest
• Built compiled, local-first developer CLI automating 5-stage AI engineering harness (grill → spec → plan → review → ship)
• Implemented unified host adapters for Claude, GPT-4, and local models with automated verification gates and immutable JSONL state tracking
• Eliminated fragile background daemon architecture in favor of stateless event-driven execution (documented in ADR-0001)"

### GitHub Profile Best Practices

**Profile optimization:**
- Pin 3-4 best projects to profile (use pin feature)
- Each pinned repo needs excellent README:
  - Clear description and motivation
  - Installation/setup instructions
  - Usage examples with screenshots/GIFs
  - Architecture overview or technical deep-dive
  - Tech stack and dependencies
  - License

**README quality signals:**
- Table of contents for longer docs
- Badges (build status, coverage, version) IF accurate
- Demo links or video walkthroughs
- Contributing guidelines (shows you think about collaboration)
- Well-structured code with comments

**Code quality signals:**
- Consistent style and formatting
- Meaningful commit messages
- Branch strategy for larger projects
- Tests (even if not 100% coverage)
- No committed secrets, API keys, or sensitive data

**What NOT to do:**
- Empty repos with "Coming soon" or "Work in progress"
- Forked repos with zero modifications in pins
- Inconsistent activity (huge gaps suggest abandonment)
- Copy-pasted code without attribution
- Tutorial projects presented as original work

### Open Source Contributions

**How to present contributions honestly:**

**Merged contributions (strongest signal):**
- "Contributed to [Project]: [Specific feature/fix] ([PR #])"
- Link directly to merged PR in GitHub
- Example: "Authored offline hierarchical clustering algorithm with 52 unit tests ([PR #8919](link)), adopted downstream in core implementation"

**Unmerged but quality contributions:**
- "Diagnosed and documented [bug] in [project], filed detailed issue report ([Issue #])"
- Only mention if issue was acknowledged/discussed by maintainers
- Example: "Identified WebGL memory leak in Electron app, authored detailed reproduction ([Issue #8438](link))"

**DO NOT claim:**
- ❌ Unmerged PRs as "contributions" without context
- ❌ Issues filed that were closed as "not a bug" or ignored
- ❌ Downstream merges by others as your direct authorship
- ❌ Fork repos as contributions to original project

**Appropriate framing:**
- "Contributed X to open source [Project]" — only for merged work
- "Collaborated on [Project] community by [specific contribution]"
- "Active participant in [Project] development, filed Y issues, submitted Z PRs"

### Addressing Unvalidated Work Authentically

**For self-funded projects without users/revenue:**

**What you CAN say:**
- Technical achievements: "Built X using Y technology achieving Z performance"
- Scope of work: "Architected N-component system with M integrations"
- Engineering velocity: "Shipped MVP in X weeks"
- Learning outcomes: "Explored [technology/approach] to solve [problem]"

**What you CANNOT say:**
- ❌ "Production-ready platform" (implies actual production use)
- ❌ "Serving thousands of users" (when you have none)
- ❌ "Scaled to handle X requests" (when never tested at scale)
- ❌ "Proven ROI" or revenue claims (when self-funded with no customers)

**Honest framing approaches:**

**Option 1: Focus on technical accomplishment**
"Built wearable AI pendant integrating ESP32-S3, custom CAD enclosure, and cloud memory capture pipeline"

**Option 2: Frame as R&D/exploration**
"Prototyped real-time voice agent system to explore low-latency interrupt handling and semantic turn detection"

**Option 3: Emphasize learning and iteration**
"Developed multi-agent consensus engine to understand orchestration patterns across LLM providers"

**Avoid qualifiers that undermine credibility:**
- ❌ "Just a side project" (implies low quality)
- ❌ "Still in early stages" (suggests incomplete)
- ❌ "Not production-ready yet" (defensive, unnecessary)
- Better: state what it IS, not what it isn't

## Section 5: Credibility & Authenticity

### Writing Strong Claims Without Inflating

**The credibility pyramid (bottom = strongest):**

1. **Verifiable facts** (strongest)
   - Specific technologies, versions, configurations
   - Measurable performance metrics
   - Links to code, demos, documentation
   - Dates, timelines, scope

2. **Demonstrable skills**
   - Projects that prove capability
   - Code samples reviewers can inspect
   - Technical decisions you can explain

3. **Accurate descriptions**
   - Precise language about your role ("built" vs "contributed to" vs "participated in")
   - Honest scope ("prototype" vs "production system")
   - Clear attribution (individual vs team work)

4. **Buzzwords and claims** (weakest)
   - "Cutting-edge," "innovative," "passionate"
   - "Expert" without evidence
   - Vague impact statements

**How to strengthen weak bullets:**

**Weak:** "Worked on AI system improving user experience"
**Better:** "Built recommendation engine using collaborative filtering, increasing user session time by 18%"

**Weak:** "Led development of scalable backend infrastructure"
**Better:** "Architected FastAPI microservices handling 5K requests/sec with Redis caching, deployed on AWS ECS"

**Weak:** "Expert in machine learning and deep learning"
**Better:** "Trained and deployed 15+ PyTorch models for NLP and computer vision tasks, with production experience in model quantization and optimization"

### Red Flags That Trigger Skepticism

**From recruiter and hiring manager perspective:**

**Content red flags:**
1. **Inflated titles**
   - "Lead Engineer" for solo projects
   - "Chief [X] Officer" at 23 years old with no team
   - "Architect" with 1 year experience

2. **Buzzword overload**
   - Every sentence contains "innovative," "cutting-edge," "paradigm-shifting"
   - Generic claims without specifics
   - Focus on what things ARE rather than what they DO

3. **Vague impact statements**
   - "Significantly improved performance"
   - "Greatly enhanced user experience"
   - "Substantially reduced costs"
   - (All need actual numbers)

4. **Technology soup**
   - Listing 50+ technologies suggesting surface-level exposure
   - Incompatible tech stacks (signals copy-paste from job descriptions)
   - Claiming expertise in technologies from 2025 in 2026 (impossible timing)

5. **Scale mismatches**
   - "Scaled system to millions of users" at seed-stage startup
   - "Enterprise-grade platform" built solo in 2 weeks
   - Claims that don't match company/role context

6. **Attribution problems**
   - Taking credit for open source project's work by contributing minor PR
   - "Built [massive system]" when you joined late-stage
   - Solo claims for work clearly requiring teams

**Format/presentation red flags:**
1. **Obvious template over-use** (same phrasing as thousands of other resumes)
2. **Spelling/grammar errors** especially in technical terms
3. **Inconsistent formatting** (signals lack of attention to detail)
4. **Generic objective statements** ("Seeking challenging position to leverage my skills...")
5. **Irrelevant information** (high school achievements, unrelated hobbies, photos)

### The "Sniff Test" for Resume Claims

**Before including any claim, ask:**

1. **Can I prove this in an interview?**
   - If asked to explain the technology/approach in depth, could you?
   - Do you have code samples or documentation to show?

2. **Is this verifiable?**
   - Can someone check GitHub, LinkedIn, company website?
   - Are metrics based on actual data you collected?

3. **Would a teammate agree?**
   - If former colleagues read this, would they confirm?
   - Are you claiming team achievements as solo work?

4. **Is the timing plausible?**
   - Can this scope of work fit in the stated timeframe?
   - Does the tech stack make sense for the date range?

5. **Does it pass the "so what?" test?**
   - Does this bullet demonstrate value/impact?
   - Or is it just describing time spent?

**When in doubt:**
- Be more specific rather than more general
- Use "contributed to" rather than "built" for team work
- Frame as learning/exploration rather than production claims
- Link to evidence (GitHub, demo, documentation)

## Section 6: Structure & Format Consensus

### Resume Length — The 2026 Consensus

**The one-page rule is dead.**

**Current consensus across sources:**

**One page appropriate for:**
- Recent graduates (0-2 years experience)
- Career changers entering tech with minimal relevant experience
- Candidates with only internships, no full-time roles
- When you genuinely have limited relevant experience

**Two pages now standard for:**
- 3-5 years of relevant experience
- Multiple substantial projects + professional experience
- Technical roles requiring detailed skills documentation
- When one page requires sacrificing readability (cramped text, tiny fonts)

**Key principle:** Quality and relevance trump arbitrary page limits

**What changed:**
- ATS systems prioritize content relevance over length
- Digital screening eliminates printing constraints
- Remote hiring means resumes rarely printed
- Readability and white space valued over compression

**Guidelines:**
- Don't artificially compress with <10pt fonts or <0.5" margins
- Don't sacrifice white space to fit arbitrary limit
- Every bullet must earn its place (relevance > completeness)
- If second page is only 25% full, try to tighten to one

### Section Ordering

**For startup-focused resume:**
1. Header (Name, contact, GitHub, portfolio)
2. Technical Skills (lead with capabilities)
3. Projects (emphasize personal/open source work)
4. Experience (professional + internships)
5. Education (unless top-tier CS program → move to #2)

**For MNC-focused resume:**
1. Header (Name, contact, LinkedIn, GitHub)
2. Experience (professional roles first)
3. Technical Skills (ATS-optimized keywords)
4. Projects (supplement professional experience)
5. Education (or #2 if recent grad from target school)

**For hybrid/balanced:**
1. Header
2. Technical Skills (if extensive) OR Experience (if strong)
3. Experience OR Technical Skills
4. Projects
5. Education

**Optional sections:**
- **Publications/Papers**: Only if research-focused role or significant papers
- **Certifications**: Only if highly relevant (AWS Certified, specific AI/ML certs)
- **Awards/Honors**: Only if prestigious or directly relevant
- **Speaking/Teaching**: Only if positioning for senior role or community leadership matters

**Never include:**
- Objective statements (outdated, waste of space)
- References (provide separately when requested)
- Photo (inappropriate for US/Canada, can introduce bias)
- Personal details (age, marital status, religion)
- Irrelevant hobbies unless asked or unique conversation starter

### Visual Design Principles

**Typography:**
- **Font**: Sans-serif for modern tech roles (Helvetica, Arial, Calibri, Open Sans)
- **Size**: 10-12pt for body text, 14-18pt for name, 11-13pt for section headers
- **Weight**: Bold for emphasis, consistent hierarchy
- **Line height**: 1.15-1.3 for readability

**Layout:**
- **Margins**: 0.5-1 inch all sides (0.75" is safe middle ground)
- **White space**: Breathing room between sections
- **Alignment**: Left-aligned for body text, centered or left for header
- **Bullet style**: Simple circles or squares, consistent throughout

**Color:**
- Black text on white background safest for ATS
- Subtle accent color acceptable (dark blue, dark gray for headers)
- Ensure 4.5:1 contrast ratio minimum
- Test in grayscale (many print in black & white)

**Consistency signals attention to detail:**
- Same bullet format throughout
- Consistent date formatting (MM/YYYY or Month YYYY, never mixed)
- Verb tenses (past tense for previous roles, present for current)
- Spacing between sections uniform
- Capitalization patterns consistent
