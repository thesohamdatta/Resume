Backend was difficult and the user mainly adapted/tweaked existing open-source/backend infrastructure rather than building the full backend from scratch.

- Omi should NOT be a separate experience/project. Mention contribution briefly under Aura or as supporting evidence.
- The user wants anti-AI-slop writing: short, concrete, human, mature, understated. Avoid fabricated impact, buzzwords, generic corporate phrasing, and unsupported metrics.

## Research principles already established
Use credible resume guidance from MIT, Yale, and relevant startup hiring guidance. Core principles already adopted:
- Tailor the resume to the target company/role.
- Prefer action + technical work + result/impact when real evidence exists.
- One page for this experience level.
- Remove padding and repetition.
- Use standard headings and readable formatting for ATS-oriented versions.
- Startup resumes should make ownership, shipping, business/product awareness and intentional breadth visible.
- Do not use invented metrics or inflated titles/claims.

## Important weaknesses identified during grilling
- Breadth is ahead of depth in some areas, especially backend/systems.
- Heavy use of coding agents is productive but creates a risk of shallow technical understanding; the user should be able to explain key system flows without the agents.
- The resume can sound like a tool inventory if too many frameworks/providers are listed.
- Aura can accidentally sound like a wrapper around Omi unless the user's own enclosure/hardware/product/software work is made explicit.
- MIA and voice projects need concrete behaviors/evidence, not only technology lists.
- Old experience (Reliance, PES) is lower-signal for AI roles and should be concise.
